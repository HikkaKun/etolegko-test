# download-bench

Небольшой скрипт для Node.js, который последовательно скачивает один и тот же
URL заданное число раз (по умолчанию 10), каждый раз дожидается полного тела
ответа и считает среднее время запроса, суммарный объём и скорость скачивания.

Внешних зависимостей нет — только стандартная библиотека Node.js.

## Требования

- Node.js **20+** (проверено на Node.js 26.12.1).
- Никакого `npm install` не нужно.

## Быстрый старт

```bash
node download-bench.mjs https://example.com/image.jpg
```

Через npm-скрипт:

```bash
npm run bench -- https://example.com/image.jpg
```

Полезные варианты:

```bash
# 3 запроса, таймаут 120 секунд на запрос
node download-bench.mjs --requests 3 --timeout 120000 https://example.com/big.png

# машиночитаемый JSON (удобно для скриптов и CI)
node download-bench.mjs --json https://example.com/big.png

# локальный тестовый сервер (по умолчанию приватные адреса запрещены)
node download-bench.mjs --allow-private http://127.0.0.1:8080/file.bin
```

## Что именно делает скрипт

1. Проверяет URL и аргументы (схема, хост, порт, диапазоны значений).
2. Выполняет `N` **последовательных** `GET`-запросов — следующий начинается
   только после того, как полностью прочитано тело предыдущего ответа.
3. Тело ответа **не сохраняется** в память и не пишется на диск: байты
   считаются по мере поступления и сразу отбрасываются.
4. Для каждого запроса замеряет время от старта запроса до последнего байта
   тела (включая установку соединения и редиректы, если они есть).
5. Печатает таблицу по каждому запросу, среднее/медиану/мин/макс, суммарный
   объём и скорость.
6. При ошибке любого запроса останавливается (fail-fast) и завершается с
   ненулевым кодом; частичный отчёт не печатается.

## Опции

| Флаг | Значение | По умолчанию | Описание |
| --- | --- | --- | --- |
| `-n`, `--requests <N>` | целое `1..1000` | `10` | число последовательных запросов |
| `-t`, `--timeout <MS>` | целое `1..86400000` | `60000` | таймаут одного запроса **целиком** (заголовки + тело), в миллисекундах |
| `--max-bytes <N>` | целое `1..8589934592` | `536870912` (512 МиБ) | максимум байт тела на один ответ |
| `--max-redirects <N>` | целое `0..20` | `5` | максимум редиректов на один запрос |
| `--allow-private` | флаг | выключен | разрешить loopback/частные/служебные адреса. **Небезопасно**, только для локальных тестов |
| `--json` | флаг | выключен | вывести отчёт в JSON вместо текста |
| `-h`, `--help` | флаг | — | показать справку |

Значения можно передавать как `--requests 3`, так и `--requests=3`.

## Единицы измерения

Это важно, потому что «мегабайты» и «мегабиты» все понимают по-разному.

- **Объём** — байты. В отчёте для читаемости используются:
  - `1 КиБ = 1024 байта`,
  - `1 МиБ = 1024 × 1024 = 1 048 576 байт`.
- **Скорость** — основная единица **МиБ/с** (мебибайты в секунду):
  `скорость (МиБ/с) = суммарный объём (байт) / общее время (секунды) / 1 048 576`.
  Дополнительно в скобках печатается **Мбит/с** в десятичных мегабитах:
  `1 Мбит = 1 000 000 бит`, то есть `Мбит/с = МиБ/с × 8 × 1 048 576 / 1 000 000 ≈ МиБ/с × 8.388608`.
- **Время** — миллисекунды и секунды. «Среднее время» — среднее арифметическое
  длительностей запросов; отдельно показывается медиана и минимум/максимум.
- **Байты в отчёте** — байты тела ответа, полученные по сети. Скрипт просит
  `Accept-Encoding: identity`, чтобы сервер не сжимал ответ. Если сервер всё
  равно сжал его (`Content-Encoding: gzip` и т.п.), считаются байты на проводе
  (сжатые), а в отчёте появляется примечание об этом.

## Как считаются метрики

- `totalBytes` — сумма байт тел всех успешных ответов.
- `totalTimeMs` — общее время прогона от старта первого запроса до конца
  последнего (включая паузы между запросами).
- `avgRequestMs` — среднее арифметическое `durationMs` по запросам.
- `medianRequestMs` — медиана длительностей.
- `minRequestMs` / `maxRequestMs` — минимум и максимум.
- `throughput.mibPerSecond = totalBytes / (totalTimeMs / 1000) / 1 048 576`.
- `throughput.mbitPerSecond = throughput.mibPerSecond × 8.388608`.

Первые запросы обычно чуть медленнее: в них входят TCP-соединение и
TLS-handshake, а последующие запросы могут переиспользовать keep-alive
соединение. Поэтому среднее и медиана могут заметно отличаться.

## Пограничные случаи и поведение

| Ситуация | Поведение |
| --- | --- |
| Нет URL, лишний аргумент, неизвестный флаг | ошибка аргументов, код выхода `2`, запросы не выполняются |
| `ftp://`, `file://`, `javascript:` и другие схемы | отклоняется на этапе разбора URL |
| Логин/пароль в URL (`https://user:pass@host/`) | отклоняется, чтобы учётные данные не попали в логи |
| Порт `0`, пустой хост, управляющие символы, URL длиннее 8192 символов | отклоняется |
| Ответ `2xx` | успех, тело дочитывается до конца |
| Ответ `204`/пустое тело | успех, `0` байт, скорость `0` |
| Ответ `3xx` с `Location` | редирект: относительный адрес разрешается, до `--max-redirects` переходов; время редиректов входит в время запроса |
| `3xx` без `Location`, битый `Location` | ошибка `REDIRECT_NO_LOCATION` / `REDIRECT_INVALID` |
| Редирект на `file://` или другой не-HTTP протокол | ошибка `REDIRECT_PROTOCOL` |
| Редирект с HTTPS на HTTP | ошибка `INSECURE_REDIRECT` (защита от downgrade) |
| Цикл редиректов | ошибка `REDIRECT_LOOP` |
| Превышен лимит редиректов | ошибка `REDIRECT_LIMIT` |
| Ответ `4xx`/`5xx` | ошибка `HTTP_STATUS`, тело не считается |
| `Content-Length` больше `--max-bytes` | ошибка `TOO_LARGE` **до** скачивания тела |
| Тело без `Content-Length` больше `--max-bytes` | ошибка `TOO_LARGE` в процессе чтения, соединение закрывается |
| Соединение оборвалось / пришло меньше `Content-Length` | ошибка `TRUNCATED` |
| DNS-ошибка | ошибка `DNS` |
| Отказ в соединении, сброс, сетевые ошибки | ошибка `NETWORK` |
| Ошибка TLS/сертификата | ошибка `TLS` |
| Превышен `--timeout` | запрос прерывается, ошибка `TIMEOUT` |
| Приватный/loopback/служебный адрес без `--allow-private` | ошибка `BLOCKED_ADDRESS`, запрос не отправляется |
| SIGINT (Ctrl+C) | запрос прерывается, код выхода `130` |

## Защита от возможных эксплойтов

Скрипт — локальная утилита, а не сервис, но URL и ответы сервера считаются
недоверенными. Реализованы следующие меры.

### SSRF и доступ к внутренней сети

- По умолчанию запрещены IPv4-диапазоны: `0.0.0.0/8`, `10.0.0.0/8`,
  `100.64.0.0/10`, `127.0.0.0/8`, `169.254.0.0/16` (включая cloud metadata
  `169.254.169.254`), `172.16.0.0/12`, `192.0.0.0/24`, `192.0.2.0/24`,
  `192.88.99.0/24`, `192.168.0.0/16`, `198.18.0.0/15`, `198.51.100.0/24`,
  `203.0.113.0/24`, `224.0.0.0/4`, `240.0.0.0/4`.
- Для IPv6 разрешён только глобальный unicast `2000::/3`; отдельно
  заблокированы `::`, `::1`, IPv4-mapped (`::ffff:127.0.0.1`), IPv4-compatible
  (`::7f00:1`), NAT64 `64:ff9b::/96`, ULA `fc00::/7`, link-local `fe80::/10`,
  multicast `ff00::/8`, документационные сети `2001:db8::/32` и `3fff::/20`,
  Teredo, ORCHID, 6to4 с приватным встроенным IPv4 и т.п.
- Проверка выполняется и для IP-литерала в URL, и для каждого адреса,
  полученного из DNS.
- **DNS rebinding**: проверка встроена в `lookup`-функцию, которую вызывает
  `net.connect`. Сокету передаются только публичные адреса, поэтому подмена
  DNS между «проверкой» и «подключением» не проходит.
- Каждый редирект проверяется заново по тем же правилам.

### Редиректы и учётные данные

- Редиректы обрабатываются вручную: проверяются протокол, хост, порт, длина
  URL и отсутствие цикла; число переходов ограничено.
- Заголовок `Location` с логином/паролем не пересылается — учётные данные
  отбрасываются.
- Скрипт не отправляет `Authorization`, `Cookie` и не хранит сессию.
- Редирект HTTPS → HTTP запрещён.

### Ресурсы и устойчивость

- Таймаут действует на весь запрос, включая тело, а не только на соединение.
- Есть лимит на размер тела; при наличии `Content-Length` превышение
  обнаруживается до скачивания.
- Тело читается потоком и сразу отбрасывается — нельзя исчерпать память
  гигантским ответом.
- Ограничены число запросов, редиректов и длина URL.
- На каждый ответ действует `--max-bytes` (по умолчанию 512 МиБ).

### Безопасность вывода и кода

- Строки от сервера (`statusMessage`, `Content-Type`, `Content-Encoding`,
  `Location`) очищаются от управляющих символов перед печатью, чтобы сервер
  не мог вставить ANSI-escape-последовательности в терминал.
- Нет `eval`, динамического `import`, запуска дочерних процессов и работы с
  файловой системой.
- Заголовки запроса фиксированы; путь и хост нормализуются парсером URL,
  Node.js дополнительно валидирует символы в запросе.
- TLS-сертификаты проверяются стандартным образом; отключения проверки нет.

### `--allow-private`

Флаг полностью отключает фильтр адресов. Используйте его только для
собственных локальных серверов и тестов. С ним скрипт может обратиться к
`localhost`, роутеру, внутренним сервисам и cloud metadata — это ровно то, от
чего защищает режим по умолчанию.

## Коды выхода

| Код | Значение |
| --- | --- |
| `0` | все запросы успешно завершены |
| `1` | ошибка выполнения (сеть, HTTP-статус, таймаут, лимит, блокировка адреса и т.п.) |
| `2` | ошибка аргументов или URL |
| `130` | прервано пользователем (SIGINT) |

В режиме `--json` при любой ошибке (включая ошибки аргументов) в `stdout`
печатается объект `{"ok": false, "error": {"code": "...", "message": "..."}}`,
а код выхода остаётся ненулевым.

## Тесты

```bash
npm test
# или
node --test test/
```

Тесты поднимают локальный HTTP-сервер и проверяют:

- разбор аргументов и URL, включая ошибки;
- блокировку приватных IPv4/IPv6-адресов (включая IPv4-mapped и 6to4) и
  разрешение публичных;
- строгую последовательность запросов;
- подсчёт байт и времени, пустой ответ `204`;
- `4xx`/`5xx`, таймаут, превышение `Content-Length` и chunked-лимита,
  оборванный ответ;
- цепочки редиректов, лимит (включая `0`), цикл, отсутствие `Location`,
  редирект на `file://`, отбрасывание логина/пароля из `Location`;
- блокировку loopback без `--allow-private` (в том числе через DNS для
  `localhost`);
- таймаут на заголовки и на медленное тело;
- текстовый и JSON-вывод CLI, включая ошибки аргументов в JSON-режиме.

## Ограничения

- Замеряется один URL; это не нагрузочный тест и не замена `curl`, `wrk` или
  специализированным бенчмаркам.
- Поддерживается только HTTP/1.1. HTTP/2, HTTP/3, SOCKS/HTTP-прокси и
  пользовательские заголовки/авторизация не реализованы.
- Считаются байты тела, а не служебные байты TCP/IP/TLS. При keep-alive
  повторные запросы не включают handshake, поэтому среднее время может быть
  ниже, чем у первого запроса.
- Таймаут прерывает запрос, но системный DNS-resolver может ещё некоторое
  время завершать уже начатый запрос — отменить `getaddrinfo` на уровне ОС
  нельзя.
- Результат зависит от кэша, CDN и текущей загрузки канала; для сравнения
  запускайте несколько прогонов.
